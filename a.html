30 Database Trade-Offs

Every Backend Engineer Eventually Faces

The decisions behind faster queries, reliable data, and scalable applications.

A database decision can look perfectly reasonable during development and become a serious problem when real users arrive. Adding indexes makes queries faster—but increases the work required for writes. Caching reduces database traffic—but can return stale information. Replication improves resilience—but introduces synchronization challenges. Sharding adds capacity—but makes queries and operations more complicated.

These aren't mistakes by default. They're trade-offs. A trade-off means improving one aspect of a system while accepting a cost somewhere else.

This handbook explores 30 decisions that backend engineers encounter while building, maintaining, and scaling applications. Each one is explained through practical scenarios rather than isolated definitions.

How To Think Like An Engineer

01 — What am I optimizing for? Speed, correctness, availability, or simplicity?

02 — What am I giving up? Every architectural benefit comes with a cost.

03 — What fails? Consider stale reads, duplicate writes, and node outages.

04 — Is this necessary? A simpler solution is often better.

The aim isn't to memorize which technology wins. It's to understand which choice fits the problem—and why.

Part I — Data Design & Models
02

SQL vs NoSQL

Should Your Data Follow Relationships or Access Patterns?

Imagine building an e-commerce application storing users, orders, products, and payments. These records are connected, and mistakes between them affect real transactions. Now imagine collecting millions of application events with varying properties. These are two very different data problems.

SQL — Relational Databases

Relational databases store information in tables with rows, columns, and constraints. They support expressive queries and transactions across related records.

Example: PostgreSQL or MySQL storing orders referencing customers and items, preserving data integrity.

NoSQL — Non-Relational

NoSQL includes document, key-value, wide-column, and graph databases. These systems use flexible data models suited to specific access patterns.

Example: A document store where laptops have RAM fields while shirts have fabric fields.

The Trade-Off Matrix

Relational (SQL) Non-Relational (NoSQL)
Structured relationships and strict constraints Data models tuned to specific query patterns
Rich relational queries (JOINs) Capabilities depend heavily on database type
Strong transactional support is standard Transaction guarantees vary by product
Schema changes require upfront planning Flexible record structures without rigid schemas

Neither option is automatically faster or more scalable. A well-designed SQL database handles enormous workloads; a poorly designed NoSQL model becomes difficult to query and maintain.

ENGINEER'S RULE: Start with the shape of your data and the queries you need to run. Choose the database afterward—not the other way around.
Part I — Data Design & Models
03

Normalization vs Denormalization

Should You Store Information Once or Duplicate It for Faster Reads?

Suppose every order needs the customer's name and shipping city. You can store customer info once in a customer table and connect each order, or copy customer info into each order record. Both approaches optimize different things.

Normalization

Each fact is stored in an appropriate place and linked using identifiers.

CUSTOMERS (id, name) ↓ ORDERS (id, customer_id) ↓ ORDER_ITEMS (order_id, product_id)

Gain: Less duplication, fewer update anomalies, clear integrity.
Cost: Complex joins required for complete reads.

Denormalization

Selected fields are copied into the record that frequently needs them.

ORDER RECORD - order_id - customer_name - shipping_city - total_price

Gain: Fewer joins, lower read latency.
Cost: Updates become complex; duplicate copies must stay synchronized.

An Important Exception: Some historical values should intentionally remain unchanged. An order should preserve the price charged at purchase time, even if the product's current catalog price changes later.

ENGINEER'S RULE: Don't duplicate everything for speed. Start with a correct model, measure expensive reads, and duplicate only what serves a clear purpose.
Part II — Distributed Consistency & Reliability
04

Consistency vs Availability

What Should Happen When Database Nodes Cannot Communicate?

Distributed databases keep data on multiple machines. What if a network partition prevents some machines from communicating? One node accepts a new account balance, but another cannot receive the update. Should the system continue answering requests from both sides with potential old data, or reject requests until consistency is protected? This dilemma is the CAP theorem.

Consistency Priority

During a partition, the system refuses certain operations rather than returning uncoordinated or conflicting results.

Benefit: Avoids accepting conflicting operations.
Cost: Requests fail or wait even if nodes are running.

Availability Priority

The system continues responding to requests on both sides of the partition, potentially using data that hasn't incorporated recent updates.

Benefit: Users can continue interacting.
Cost: Temporary stale or conflicting information.

Practical Scenarios

A banking operation verifying the latest account state must reject requests when required coordination is unavailable. Conversely, a non-critical activity feed can display cached or slightly stale information while the network recovers.

Note: CAP is specifically about network partitions. It does not mean systems must always choose between consistency and availability during normal operation.

ENGINEER'S RULE: Define what the application must guarantee during a network failure. Then decide which requests can safely continue and which must wait.
Part II — Distributed Consistency & Reliability
05

Strong vs Eventual Consistency

Can Different Users Temporarily See Different Versions of the Same Data?

A user changes their profile name. The primary database accepts the update, but a replica hasn't received it yet. One request returns the new name; another returns the old one. Is that a bug? It depends on your consistency promises.

Strong Consistency

Once a write succeeds, subsequent reads covered by that guarantee return the latest committed value.

Gain: Predictable reads, no stale surprises.
Cost: Distributed coordination increases latency during failures.

Eventual Consistency

Replicas temporarily return different values. If updates stop, replicas eventually converge to a consistent state.

Gain: Responsive reads and independent updates.
Cost: Application must tolerate stale reads and resolve conflicts.

Don't Confuse the Two Decisions

Consistency vs Availability during a partition asks what a system does when nodes cannot coordinate. Strong vs Eventual consistency asks what guarantees readers receive about data freshness. They are related, but distinct.

ENGINEER'S RULE: Choose consistency based on the consequences of stale information. A stale recommendation is harmless; a stale inventory count or account balance affects financial decisions.
Part III — Query Performance & Caching
06

Read Performance vs Write Performance

Why Making Reads Faster Can Make Writes Slower

A product catalog receives thousands of views per update, while an event collector continuously inserts new records. Your database must be optimized for the workload it actually receives.

Read-Heavy Workloads

Many users → Repeated SELECTs → Same records read often

Techniques: Indexes, caching, read replicas, precomputed results.
Cost: Indexes need maintenance, caches need invalidation, replicas need sync.

Write-Heavy Workloads

Continuous INSERT/UPDATE → DB writes → Log & index maintenance

Techniques: Append-only logs, minimal indexing.
Cost: Queries become slow and expensive without proper indexes.

A catalog justifies category indexes because users repeatedly filter by category. Conversely, a high-volume event ingestion table may not need an index on every field if some fields are never searched.

ENGINEER'S RULE: Measure the ratio and cost of reads and writes before optimizing. Optimize the entire workload against actual system requirements.
Part III — Query Performance & Caching
07

Joins vs Data Duplication

Should the Database Combine Data at Read Time or Store It Together?

Consider an orders page displaying order date, customer name, shipping city, items, and total price. This lives across multiple tables. The database can combine them via joins, or the application can store selected fields together.

Using JOINs

ORDERS ──┐ ├── JOIN ──► ORDER DETAILS CUSTOMERS┘

Gain: Less duplication, clear ownership of facts.
Cost: Complex queries; poor indexing makes large joins expensive.

Data Duplication

ORDER VIEW (denormalized) - order_id - customer_name - shipping_city - total_price

Gain: Simpler retrieval, lower read latency.
Cost: Duplicated values require update strategies and sync handling.

Remember that preserving a snapshot (such as order price at checkout time) is a business requirement, not merely a performance optimization.

ENGINEER'S RULE: Keep authoritative data modeled correctly. Optimize the read path only when added duplication is justified by measured performance needs.
Part III — Query Performance & Caching
08

Indexes vs Write Speed

The Shortcut That Makes Reads Faster Also Needs Maintenance

Searching for one customer among ten million records without an index forces the database to examine a large number of rows. An index acts like a book index, using a lookup structure to locate records efficiently.

Without Index

Query → Scan table rows → Find record (High Read Latency)

With Index

Query → Lookup Index → Direct pointer to record (Low Read Latency)

Why Not Index Every Column?

Indexes consume storage and require maintenance during data modifications. Every INSERT, UPDATE, or DELETE may require updating multiple index structures. Too many unnecessary indexes increase write overhead and resource pressure.

When Should You Add an Index?

  • The column appears frequently in selective filters or WHERE clauses.
  • Queries repeatedly sort or join using the indexed columns.
  • Query execution plans confirm the index reduces disk I/O or row scans.
ENGINEER'S RULE: Indexes are not decorative optimizations. Add them to solve measured query problems, then monitor both read improvements and write overhead.
Part III — Query Performance & Caching
09

Single-Column vs Composite Indexes

One Field at a Time—or the Exact Combination Your Query Needs?

A single-column index helps locate records using that specific field. However, many production queries filter or sort using multiple fields simultaneously, such as filtering orders by user ID and ordering by creation time.

Single-Column Index

INDEX: (user_id)

Effective when queries filter strictly by user_id alone, but inefficient for compound sorting.

Composite Index

INDEX: (user_id, created_at)

Supports queries filtering by user_id and sorting/filtering by created_at efficiently.

Why Column Order Matters

A composite index is organized according to its leading columns (Leftmost Prefix Rule). An index on (user_id, created_at) supports queries filtering by user_id, but it may not efficiently support a query filtering only by created_at.

ENGINEER'S RULE: Start with actual query patterns. Inspect execution plans, respect leftmost-prefix rules, and test performance before adding overlapping indexes.
Part IV — Transactions & Scaling
10

Transactions vs Performance

Should Several Database Operations Succeed or Fail Together?

Transferring funds between accounts requires subtracting from one and adding to another. If the first succeeds and the second fails, the system must not leave accounts in an invalid state. Transactions enforce this atomicity.

Anatomy of a Database Transaction

BEGIN TRANSACTION ├─► Debit Account A (Update balance) ├─► Credit Account B (Update balance) └─► COMMIT (or ROLLBACK on failure)

When Transactions Become Expensive

Consider a transaction that updates records and then waits for a slow external API before committing. It keeps locks and resources occupied unnecessarily, blocking concurrent operations and reducing throughput.

Better Design Pattern

Keep database transactions focused strictly on database changes that need atomicity. Perform slow external work outside the transaction, using background workflows to handle failures.

ENGINEER'S RULE: Do not remove transactions merely to improve speed when correctness depends on them. Keep transactions as short and focused as practical.
Part IV — Transactions & Scaling
11

Offset vs Cursor Pagination

Why Page 1 Can Be Fast While Page 10,000 Becomes Painful

Returning millions of posts requires pagination. Two common approaches handle this differently: offset pagination and cursor pagination.

Offset Pagination

Page 1 → OFFSET 0 Page 10,000 → OFFSET 200,000

Gain: Simple API, numbered page jumps.
Cost: Deep offsets force the database to scan and discard thousands of rows.

Cursor Pagination

Fetch 20 → Save last sort position (cursor) → Fetch WHERE id > cursor LIMIT 20

Gain: O(1) performance at any depth, robust against inserts.
Cost: Harder to jump to arbitrary page numbers.

Cursor pagination requires a deterministic sort order (such as timestamp combined with a unique ID) to handle records sharing identical timestamps.

ENGINEER'S RULE: Use offset pagination when simple page navigation matters and datasets are small. Use cursor pagination for large feeds and infinite scrolling.

Part IV — Transactions & Scaling
12

Vertical vs Horizontal Scaling

Should You Make One Database Server Bigger or Add More Servers?

When your database reaches CPU, memory, or disk I/O limits, you face a fundamental scaling choice: upgrade the existing machine or distribute workload across multiple machines.

Vertical Scaling (Scale Up)

Small Instance ──► Bigger Instance (More CPU / RAM / NVMe)

Gain: Simple operational model, minimal code changes.
Cost: Hardware ceilings, single point of failure, high cost at scale.

Horizontal Scaling (Scale Out)

DATABASE WORKLOAD │ ┌─────┼─────┐ ▼ ▼ ▼ NodeA NodeB NodeC

Gain: Near-infinite aggregate capacity and resilience.
Cost: Routing complexity, replication lag, operational overhead.

ENGINEER'S RULE: Scale vertically while it meets your requirements—it is operationally simpler. Move to horizontal scaling when storage, throughput, or availability targets demand it.
Part IV — Transactions & Scaling
13

Read Replicas vs Read-After-Write Consistency

Why a User Can Save Something and Still See the Old Value

Read replicas offload read traffic from the primary database. However, asynchronous replication takes time, leading to replication lag where a user saves a profile update but immediately reads stale data from a lagging replica.

The Replication Lag Scenario

User updates profile → Primary DB saves → Replica is catching up ──x (Lag) User reads immediately from replica ──► Returns OLD profile data

Architectural Mitigations

  • Route critical reads to Primary: Direct users to the primary database immediately after they perform a write operation.
  • Session Consistency: Ensure a user's session always reads from a replica that has caught up with their latest write sequence number.
  • Accept Stale Reads: For non-critical data (like view counts or public catalogs), eventual consistency is acceptable.
ENGINEER'S RULE: Route reads according to freshness requirements. A public catalog tolerates stale data; a user checking their own recent transaction expects immediate accuracy.
Part IV — Transactions & Scaling
14

Sharding vs Simplicity

When One Database Is No Longer Enough

Sharding divides a dataset across multiple database instances, assigning a subset of data to each shard via a routing key.

What Sharding Improves

• Aggregate storage capacity beyond single-node disk limits.
• Distribution of write workload across machines.

What Sharding Makes Harder

• Cross-shard JOINs and distributed transactions.
• Handling hotspot keys and uneven traffic distribution.

The Shard-Key Dilemma

If most requests target a single shard (e.g., a celebrity user account), that shard becomes an extreme hotspot regardless of how many other shards exist. Choosing a shard key requires balancing data distribution and query efficiency.

ENGINEER'S RULE: Do not shard simply because you have many users. Maximize indexes, caching, vertical scaling, and read replicas first. Shard only when storage or write throughput demands it.
Part IV — Transactions & Scaling
15

Partitioning vs Operational Complexity

Should One Large Table Be Split into Smaller Logical Pieces?

Partitioning divides a single logical table into smaller physical partitions (by date, region, or tenant) while allowing applications to query the table as a single unit.

Time-Based Partitioning

ORDERS Table ├── Partition: 2024 ├── Partition: 2025 └── Partition: 2026

Partition Pruning: Queries targeting 2026 skip 2024 and 2025 partitions entirely.

Partitioning vs Sharding

Partitioning divides a table into logical segments inside a database.

Sharding distributes data across completely separate database nodes or cluster deployments.

ENGINEER'S RULE: Partition when datasets have a natural division (like time or region) that improves query pruning or archival maintenance. Don't add partitions without measured benefits.
Part V — Architecture & Caching
16

Shared Database vs Database-Per-Service

Should Multiple Services Use the Same Database?

In microservice architectures, deciding whether services share a database or maintain isolated stores directly impacts team autonomy and system coupling.

Shared Database

Orders ──┐ Payments ─┼──► Shared DB Inventory ┘

Gain: Simple early setup, easy cross-domain queries.
Cost: Tightly coupled schemas; one team's migration breaks another service.

Database-Per-Service

Orders → Order DB Payments → Payment DB Inventory → Inventory DB

Gain: Autonomous ownership, independent scaling.
Cost: Complex cross-service queries and eventual consistency workflows.

ENGINEER'S RULE: A shared database is fine for early monoliths. Move toward database-per-service when teams need true operational independence—not just because microservices are trendy.
Part V — Architecture & Caching
17

Cache vs Database

Should Every Request Reach the Database?

Databases serve as the authoritative system of record, while caches store temporary copies of frequently accessed data to serve subsequent reads faster.

The Cache-Aside Pattern Flow

Request → Check Cache (Redis) ├── HIT → Return cached value immediately └── MISS → Query Database → Populate Cache → Return result

Trade-Offs of Caching

What you gain: Sub-millisecond latency for repeated reads, reduced database load, and higher throughput capacity.
What it costs: Additional infrastructure memory, cache invalidation complexity, stale data risks, and handling cache outages without crashing the primary database.

ENGINEER'S RULE: Cache data that is frequently read and whose freshness requirements are well understood. Keep authoritative truth in the primary database.
Part V — Architecture & Caching
18

Cache Freshness vs Performance

How Long Can Your Application Use an Old Value?

Cache Time-to-Live (TTL) configuration controls how long entries remain valid. Longer TTLs maximize cache reuse but increase stale data duration; shorter TTLs ensure freshness but increase database read frequency.

Short TTL

Expires quickly → Frequent DB refreshes → Fresher data, higher DB load

Long TTL

Remains valid long → Fewer refreshes → High cache hit rate, stale risk

The Core Question

Instead of asking "How long should this cache live?", ask: "What is the consequence if this value is stale for 30 seconds?" Product catalogs tolerate stale data; security permissions and financial balances do not.

ENGINEER'S RULE: Choose TTL based on freshness tolerance and workload. For critical state changes, use explicit invalidation rather than relying solely on time-based expiry.
Part V — Architecture & Caching
19

Precomputation vs Real-Time Queries

Should You Calculate a Result When Requested or Beforehand?

Dashboards displaying total sales and regional revenue can calculate metrics in real time upon request or precompute them in the background for instant retrieval.

Real-Time Queries

User opens dashboard → Scan millions of rows → Aggregate live → Return result

Gain: Always reflects latest committed data.
Cost: High CPU/disk load, slow response times under concurrency.

Precomputation

Background worker → Aggregate hourly/daily → Store summary → Instant read

Gain: Instant dashboard loads, zero heavy queries.
Cost: Data is slightly delayed; requires reliable background pipeline.

ENGINEER'S RULE: Use real-time calculation when freshness is essential and query costs are low. Precompute results when expensive aggregations are requested repeatedly and delays are tolerable.
Part V — Architecture & Caching
20

Materialized Views vs Storage and Refresh Cost

Should the Database Store the Result of an Expensive Query?

A standard database view evaluates its query definition on every access. A materialized view physically stores the result of an expensive query, allowing subsequent requests to read saved results instantly.

Without Materialized View

Dashboard Request → JOIN 5 tables → GROUP BY & SUM → High Latency

With Materialized View

Dashboard Request → Read pre-calculated table rows → Instant Response

Trade-Offs

Gains: Faster reads for repeated heavy queries and simplified reporting structures.
Costs: Additional disk storage, background refresh overhead, and potential lag between source updates and refreshed view data.

ENGINEER'S RULE: Materialize queries when they are expensive, frequently repeated, and tolerant of asynchronous refresh schedules.
Part VI — Production Operations
21

Connection Pooling vs Resource Usage

Why Opening More Database Connections Doesn't Make You Faster

Opening a database connection requires handshake overhead and memory allocation. Creating a new connection for every web request wastes resources, leading to connection pooling.

The Connection Pool Sizing Dilemma

App Instances (10) × Max Pool Size (100) = 1,000 Potential DB Connections!

Too few connections: Requests queue up waiting for a free connection, increasing latency.
Too many connections: The database spends excessive memory and CPU cycles managing active sessions and thread context switching, degrading overall throughput.

ENGINEER'S RULE: Start with a measured connection pool size. Monitor active connections, queue wait times, and database saturation. Beyond optimal range, more connections degrade performance.
Part VI — Production Operations
22

Hot vs Cold Storage

Should All Data Live on the Fastest—and Most Expensive—Storage?

Recent orders are queried constantly, while old audit logs are accessed rarely. Storing all data on high-performance NVMe storage wastes budget.

Hot Storage

• High IOPS, low latency.
• Active customer profiles, current orders.
• Expensive per gigabyte.

Cold / Archival Storage

• Lower cost per gigabyte.
• Historical logs, compliance records.
• Slower retrieval times.

Data Lifecycle: New Data (Hot Storage) ──► 90 Days (Warm Tier) ──► 1 Year (Cold Archive)
ENGINEER'S RULE: Design storage tiers around access frequency and retention policies. Never archive data to save money without verifying restoration time and compliance needs.
Part VI — Production Operations
23

Fail-Open vs Fail-Closed

What Should Your Application Do When a Database Dependency Fails?

If Redis cache goes down, should your API fail completely or fall back to reading directly from the primary database?

Fail-Open

The application bypasses the failed dependency and falls back to a secondary path.

Risk: Fallback queries can overload the primary database and trigger cascading failures.

Fail-Closed

The application rejects operations when required security or consistency guarantees cannot be verified.

Risk: Higher user-facing downtime during minor outages.

ENGINEER'S RULE: Fail open only when fallbacks are safe and rate-limited. Fail closed when proceeding without the dependency violates security, financial correctness, or business rules.
Part VI — Production Operations
24

Synchronous vs Asynchronous Replication

Should a Write Wait for a Replica to Confirm It?

Replication copies data across nodes. The critical architectural decision is when the system reports a write as successful relative to replication progress.

Synchronous Replication

Write → Primary → Replica Confirms → Success Response

Gain: Zero data loss on primary failure.
Cost: Higher write latency, reduced write availability if replicas drop.

Asynchronous Replication

Write → Primary Saves → Success Response → Replica Catches Up Later

Gain: Low write latency.
Cost: Recent acknowledged writes can be lost if primary fails before syncing.

ENGINEER'S RULE: Use replication guarantees matching your durability and latency requirements. Never assume asynchronous replication guarantees zero data loss.
Part VI — Production Operations
25

Fast Failover vs Potential Data Loss

When the Primary Database Fails, How Quickly Should Another Node Take Over?

Promoting a replica to primary during an outage restores availability quickly, but the replica may not contain every recent write from the failed primary.

Key Disaster Recovery Metrics

RTO (Recovery Time Objective): How long can the service remain unavailable during an outage?

RPO (Recovery Point Objective): How much recent data loss can the business tolerate?

Prioritizing instant failover restores uptime quickly but risks dropping un-replicated transactions. Prioritizing strict data preservation requires confirmation checks that can extend downtime during leader elections.

ENGINEER'S RULE: Choose failover procedures based on explicit RTO and RPO targets. Test them under realistic failure simulations instead of assuming automatic promotion is safe.
Part VII — Specialized Storage & Search
26

OLTP vs OLAP

Should the Database Focus on Transactions or Large-Scale Analysis?

Handling day-to-day user transactions (OLTP) requires fast single-row lookups and ACID guarantees, whereas analytical reporting (OLAP) requires scanning millions of historical records.

OLTP (Online Transaction Processing)

• Creating orders, updating user profiles.
• Low latency, row-oriented storage.
• Priority: Correct updates & ACID concurrency.

OLAP (Online Analytical Processing)

• Quarterly revenue trends, cohort analysis.
• Columnar storage, fast table scans.
• Priority: High-speed analytical aggregates.

Running heavy analytical queries against an OLTP production database competes for CPU, memory, and disk I/O, degrading user-facing performance.

ENGINEER'S RULE: Use OLTP for operations and OLAP for analytics. Separate them via ETL/CDC pipelines so reporting queries never starve production transactions.
Part VII — Specialized Storage & Search
27

Database vs Search Engine

Why a Database Query Is Not Always the Best Way to Search Text

Relational databases excel at exact filtering and structured records, whereas search engines (like Elasticsearch or OpenSearch) specialize in full-text search, tokenization, and relevance ranking.

Database

Authoritative product records, exact ID lookups, structured relationships, and ACID transactions.

Search Engine

Full-text search, BM25 relevance ranking, fuzzy matching, faceted filtering, and autocomplete.

Product DB (Source of Truth) ──(CDC / Sync)──► Search Index ──► Fast Search Results
ENGINEER'S RULE: Use a database for authoritative records and structured operations. Add a search engine when relevance-based discovery and full-text search justify the extra infrastructure.
Part VII — Specialized Storage & Search
28

Database vs Vector Database

Finding Exact Records vs Finding Semantically Similar Information

Traditional databases retrieve exact matches via structured indexes. Vector databases convert content into numerical embeddings and perform geometric similarity search.

Traditional Database

Find all orders where user_id = 42. Optimized for exact identifiers and deterministic filters.

Vector Database

Find documents whose semantic meaning matches this user question. Optimized for ANN proximity search.

Documents ──► Embedding Model ──► Vectors ──► Similarity Search (ANN) ──► Relevant Chunks
ENGINEER'S RULE: Use structured queries for exact facts and vector search for semantic similarity. Combine both when applications require hybrid retrieval capabilities.
Part VIII — Architecture & Strategy
29

Single Source of Truth vs Specialized Read Stores

Why Keep Multiple Copies of Data If the Application Needs Only One Truth?

As systems scale, relying on a single database for every access pattern fails. Modern systems use relational DBs for truth, Redis for caching, search engines for discovery, and warehouses for analytics.

AUTHORITATIVE DATA (PostgreSQL)
│
├──► Cache Store (Redis)
├──► Search Index (OpenSearch)
└──► Analytics Warehouse (Snowflake)

Gain: Fast retrieval tailored to specific workloads.
Cost: Updates must be propagated across stores, temporary staleness occurs, and synchronization failures create data inconsistencies.

ENGINEER'S RULE: Every important field needs a clear ownership rule. Specialized stores require explicit update, freshness, and recovery strategies rather than becoming competing sources of truth.
Part VIII — Architecture & Strategy
30

Database Simplicity vs Scale

Why the Most Complex Architecture Is Not Automatically the Best One

Launching a product with a few hundred users does not require sharding, replicas, multiple specialized databases, and distributed caching. Sophistication is not suitability.

The Simple Start

Application ──► One Well-Managed Database

Few moving parts, straightforward debugging, easy transactions, and low operational costs.

The Distributed Design

App ──► Routing ──► Replicas / Shards / Caches

Aggregate capacity and resilience, at the cost of distributed failure modes and synchronization complexity.

ENGINEER'S RULE: Start with the simplest architecture meeting your correctness and performance requirements. Add complexity only when evidence or scale demands it.
Epilogue • Architectural Summary
31

Great Database Design Isn't About Choosing The Most Powerful Tool.

It's about understanding what your application needs—and what each decision costs.

• Faster reads may mean more indexes and higher write overhead.

• More availability may mean accepting stale data during network partitions.

• Distributed storage introduces complex coordination and replication lag.

• Specialized stores require robust synchronization pipelines.

Before choosing any technology, ask:

01 — What am I optimizing for?
02 — What am I sacrificing?
03 — What happens when it fails?
04 — Can I solve this more simply?

There is no universally perfect database architecture. There is only a design that fits your data, workload, reliability requirements, and constraints.

Learn the trade-offs. Make decisions deliberately. Build accordingly.
